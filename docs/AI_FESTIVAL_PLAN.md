## 1. 현 프로젝트와의 관계

현재 저장소는 **뉴스 읽기 보조 도구**이고, 과제는 **질의응답 에이전트**다. 제품 종류가 다르므로
그대로 제출할 수는 없다. 다만 아래 자산은 그대로 이식 가능하며, 일부는 이 과제의 차별화 지점에
정확히 해당한다.

| 기존 자산 | 위치 | 과제에서의 역할 |
|---|---|---|
| Gemini 호출 계층 (모델 자동탐색·폴백·구조화 출력 강제·JSON salvage) | `app/translator.py:164,231,252` | Agent의 LLM 클라이언트. 모델 교체 가능한 추상화가 이미 있음 |
| 테마 키워드 → 상품 매칭 | `app/products.py:28` | **뉴스 ↔ 상품 연결 이력** 생성기 (평가 예시 4번의 정답 경로) |
| 경제·채권·펀드 용어사전 58개 | `app/data/glossary.json` | 온톨로지 `rdfs:label` / 동의어 사전, Entity Resolution 정규화 |
| 기사 본문 추출기 | `extension/content_script.js` | 비정형 뉴스 수집 파이프라인의 파서 |
| FastAPI + 배포 구성 | `app/main.py`, `Procfile`, `DEPLOY.md` | 평가용 API 서버 (09.07~09.20 상시 활성 요구) |
| Chrome 확장 UI | `extension/` | 본선 라이브 시연용 데모 표면 |

**버리는 것**: `app/data/products.json`의 하드코딩 21종, `app/stocks.py`의 모의 시세.
주최 측 마스터 데이터가 기준 데이터이며, 상충 시 주최 측 데이터가 우선한다.

## 2. 왜 뉴스 파이프라인이 차별화가 되는가

평가 질의 예시 5문항 중 3문항은 **마스터 데이터만으로는 풀 수 없다.**

| No | 질의 | 마스터에 없는 것 | 필요한 외부 데이터 |
|---|---|---|---|
| 2 | 국민성장펀드의 구조와 투자전략 동향 | 운용전략 서술 (공모펀드마스터는 보수 정보도 미포함) | 투자설명서·운용보고서 PDF |
| 3 | 캠브리콘이 편입된 중국 반도체 ETF | 구성종목(holdings) | 운용사 PDF·공시 |
| 4 | 최근 6개월간 우주항공 테마와 **연결 이력**이 있는 ETF | 테마-시점 연결 이력 | **뉴스 타임라인** |
| 5 | 에코프로의 **자회사**를 편입한 ETF의 위험요인 | 기업 지배구조, holdings | 공시 + PDF |

과제 규칙상 외부 비정형 데이터 수집은 허용되며, 기술제안서 배점(40%)의 첫 질문이
*"어떤 특화 데이터를 어떻게 수집·정제했는가"*다. 뉴스→테마→상품 연결 그래프는
대부분의 팀이 만들지 않을 축이므로 여기에 집중한다.

## 3. 목표 아키텍처

```
[수집]  주최 마스터 4종 (xlsx)          [비정형] 뉴스 / 투자설명서 / 운용보고서 / 공시
           │                                        │
           │                            Parsing: PDF·PPT → Markdown  (과제 필수요소 1)
           ▼                                        ▼
[온톨로지] ontology/common.ttl + bond_kr / etf_kr / etf_gl / fund_pub   (필수 제출물)
           │
           ▼
[KnowledgeBase]  ┌ DuckDB      정형 마스터 14.5만 건, 집계·정렬·비교 연산
                 ├ Vector DB   운용전략 서술·위험요인·투자설명서 청크
                 └ Graph       상품 ─ 테마 ─ 뉴스 ─ 기업 ─ 자회사 ─ holdings
           │
           ▼
[Intent Router]  질의 분류 → SQL형 / 서술형 / 그래프형 / 하이브리드 / 답변불가
           │        └ Entity Resolution: 상품명·기업명·등급값 정규화
           ▼
[Retrieval]  NL2SQL (스키마 프롬프트 + 컬럼 사전 + 등급 서열 인코딩)
           │  Vector 검색 / Graph 순회 결과와 결합
           ▼
[Answer Generator]  Evidence 조립 → 생성 → 사후 근거 검증 가드
           │
           ▼
GET /answer  { question_id, question, retrieved_context, think_trace, answer }
```

### 검색 모드 라우팅 (평가 예시 기준)

| 모드 | 판별 신호 | 해당 예시 |
|---|---|---|
| SQL | 수치 조건·정렬·비교·집계 | 1번 (AA- 이상 원화채권), "총보수 낮고 AUM 큰 3개" |
| Vector | 서술·전략·구조 질의 | 2번 (투자전략 동향) |
| Graph | 편입/포함/연결/관계 | 3·4·5번 |
| Hybrid | 관계 + 수치 조건 | 5번 (자회사 편입 ∩ 순자산 상위) |

## 4. 답변 불가 처리 — 배점 직결 모듈

> 답변 불가 질의 5문항 포함 예정. 답변을 생성하면 **감점**.
> '확인할 수 없음' 명시 또는 필요한 조건 역질문이 정답 처리.

30문항 중 5문항(약 17%)이며, 잘못 답하면 감점이므로 실질 가중치는 그 이상이다.
제시된 3개 예시는 서로 다른 3종의 실패 유형이므로, 가드도 3종으로 나눠 구현한다.

| 가드 | 검사 내용 | 해당 예시 | 응답 |
|---|---|---|---|
| G1 값 도메인 검증 | 질의 속 값이 컬럼의 허용 도메인에 있는가 | "신용등급 **AAAA**" — 등급 체계에 없는 값 | 확인 불가 + 실제 등급 체계 안내 |
| G2 엔티티 해결 실패 | 고유명사가 KB의 어떤 엔티티에도 매핑되지 않음 | "**Kimi** 관련 투자 상품" | 확인 불가 |
| G3 상품명 정확매칭 실패 | 유사 상품은 있으나 임계치 미달 | "**KODEX AI로봇** ETF" | 확인 불가 + 유사 상품 역질문 |

**설계 원칙**: 가드는 Retrieval **이전**에 돌린다. LLM에 도달하기 전에 차단해야
환각이 원천 차단되고 응답 시간도 절약된다. 이 모듈은 구현 난이도 대비 배점 기여가
가장 높으므로 **1주차에 먼저 만든다.**

## 7. 즉시 확인해야 할 리스크

1. **데이터 확보 여부** — 마스터 xlsx가 없으면 1주차 전체가 블로킹된다. 최우선.
2. **제출 저장소** — 산출물은 *주최 측 제공 Github Organization 내 Private Repository*에
   Push해야 한다. 현재 공개 저장소는 개발용이며 제출처가 아니다.
3. **LLM 활용 기준 미공지** — 자료에 *"필수 LLM 활용 기준 관련: 추후 공지 예정"*이라고만
   되어 있다. 특정 모델이 강제될 수 있으므로 `src/llm.py`는 교체 가능한 인터페이스로 유지한다.
4. **응답 시간이 평가 항목** — 문항당 60초 이내 권장. 현재 `translator.py:164`의
   모델 자동 탐색은 후보를 순차 시도하므로 그대로 쓰면 시간 예산을 초과한다.
   기동 시 1회 탐색 후 결과를 고정해야 한다.
5. **뉴스 데이터의 기준일 정합성** — 마스터 스냅샷은 2026-07-11 기준이다. 뉴스에서 파생한
   연결 이력이 이 시점과 충돌하지 않도록 시점을 함께 표기한다.

## 8. 답변 원칙 (전 모듈 공통 제약)

- 모든 답변은 데이터를 근거로 생성하고 참조 데이터를 `retrieved_context`에 표시한다.
- 확인 불가 질의는 '확인할 수 없음' 명시 또는 필요한 조건을 역질문한다.
- **데이터에 근거 없는 수익률 전망·단정적 투자 추천은 생성 금지.**
  (현재 프로젝트의 "투자 권유가 아닌 참고 정보" 문구 정책을 그대로 승계한다.)
- 확인 불가 응답도 200 OK + 동일 스키마를 유지한다.
